# 数据模型设计（完整版 v6.3）

> **版本更新说明**：
> - **v6.2 → v6.3（任务9增强版）**：
>   1. **新增 `kb_agent_loop_traces`**：记录 ReAct 循环中每一步的 Thought/Action/Observation 全轨迹，支撑 LangGraph/DeepAgents 的调试、成本审计与 Bad Case 分析。
>   2. **新增 `kb_evaluation_results`**：记录评估节点（Evaluator）的多维度置信度（相关性/覆盖度/权威性/一致性）及矛盾/缺失信息明细，实现“自主评估”的可解释性。
>   3. **新增 `kb_pending_questions`**：持久化“反问用户”的等待队列，支持异步恢复与超时管理，解决任务9中“信息不足时主动反问”的暂停-恢复机制。
>   4. **修改 `kb_sessions`**：增加 `agent_state`（序列化的 LangGraph State，用于恢复现场）和 `loop_status`（标识当前会话的 Agent 执行状态）。
>   5. **修改 `kb_query_logs`**：增加多步规划标记、总循环轮数、最终决策及回答预览，实现顶层查询视角的完整追踪。
> - **v6.1 → v6.2**：状态解耦（`indexing_status` + `lifecycle_status`）、审批字段、通知审计表。
> - **v6.0 → v6.1**：融合任务6（Rerank追踪）与任务7（排序日志）。

数据模型设计服务于两个核心场景：**写入**（文档预处理后入库）和**读取**（检索时快速过滤和召回）以及**多步推理**（ReAct 循环与自主评估）。整体分为五块：
1. **MySQL**：存储元数据、切块原文、标签、版本、反馈、路由日志、会话上下文、查询日志、召回日志（含Rerank追踪）、排序日志、MCP 配置与映射、通知日志（v6.2）、**Agent循环轨迹（v6.3新增）**、**评估明细（v6.3新增）**、**待反问队列（v6.3新增）**等结构化数据。
2. **Elasticsearch**：存储切块文本，用于关键词检索（BM25）和元数据过滤。
3. **向量数据库（Milvus）**：存储切块向量，用于语义检索。
4. **配置中心（Nacos/Apollo）**：存储全局字典、路由运行时参数（含MCP）、意图理解策略、混合检索参数（含Rerank配置）、排序权重（含个性化角色权重）等热配置。
5. **对象存储（MinIO/OSS）**：存储原始文档文件及解析缓存。


## 一、MySQL 数据模型

一共需要 **19张** 核心表（v6.2的16张 + v6.3新增3张）。

### 1.1 文档主表：`kb_documents`（📌 v6.2 重构）

| 字段名 | 类型 | 约束 | 描述 |
| :--- | :--- | :--- | :--- |
| `id` | bigint | PRIMARY KEY AUTO_INCREMENT | 自增主键 |
| `doc_uuid` | varchar(64) | UNIQUE NOT NULL | 文档唯一标识，API使用 |
| `file_name` | varchar(255) | NOT NULL | 原始文件名 |
| `file_hash` | varchar(64) | INDEX | 全文SHA-256，用于版本比对 |
| `file_path` | varchar(512) | | 对象存储路径 |
| `source_kb` | varchar(32) | NOT NULL | 来源知识库：fund/credit/compliance等 |
| `doc_type` | varchar(32) | | 文档类型：研报/公告/合同等 |
| `version` | varchar(16) | DEFAULT 'v1.0' | **当前线上生效的版本号** |
| `indexing_status` | tinyint | DEFAULT 0 | **索引技术状态**：`0`-待处理/处理中 / `1`-已索引（三库一致） / `2`-异常 |
| `lifecycle_status` | varchar(20) | DEFAULT 'draft' | **业务生命周期状态**：`draft` / `published` / `archived` / `pending_approval` / `rejected` |
| `previous_lifecycle_status` | varchar(20) | NULL | **回退锚点**：仅当 `lifecycle_status` 为 `pending_approval` 或 `rejected` 时记录，驳回时恢复至此状态 |
| `pending_version` | varchar(16) | NULL | **待审批的新版本号**：仅 `pending_approval` 状态下有值，审批通过后覆盖 `version` |
| `approved_by` | varchar(64) | NULL | **审批人ID**（确认索引/驳回的操作人） |
| `approved_at` | datetime | NULL | **审批时间** |
| `reject_reason` | text | NULL | **驳回原因**（驳回时必填） |
| `published_date` | datetime | INDEX | 文档原始发布日期（业务属性，非系统发布时间） |
| `retry_count` | tinyint | DEFAULT 0 | 索引重试次数（超过3次停止自动重试） |
| `last_error` | text | NULL | 最后一次失败堆栈或错误信息 |
| `processing_started_at` | datetime | NULL | 最近一次开始处理的时间（用于检测卡死任务） |
| `indexed_at` | datetime | NULL | 三库全部写入完成的时间 |
| `parser_engine` | varchar(64) | NULL | 解析引擎及版本，如"mineru-1.2.0" |
| `created_at` | datetime | DEFAULT CURRENT_TIMESTAMP | 创建时间 |
| `updated_at` | datetime | DEFAULT CURRENT_TIMESTAMP ON UPDATE | 更新时间 |

**索引**：
```sql
CREATE INDEX idx_source_kb ON kb_documents(source_kb);
CREATE INDEX idx_file_hash ON kb_documents(file_hash);
CREATE INDEX idx_indexing_status ON kb_documents(indexing_status);
CREATE INDEX idx_lifecycle_status ON kb_documents(lifecycle_status);
CREATE INDEX idx_pending_approval ON kb_documents(lifecycle_status, created_at); -- 待审批列表查询
```

## 六、跨库一致性保障（📌 v6.3 更新 Agent 相关规则）

| 场景 | 处理方式 |
| :--- | :--- |
| **写入顺序** | 先写MySQL（`indexing_status=0`）→ 再写ES → 再写Milvus → 更新MySQL `indexing_status=1` |
| **异常恢复** | 定时补偿任务扫描 `indexing_status IN (0,2)` 且超过5分钟的记录，重试最多3次 |
| **逻辑删除（软删除）** | `kb_chunks.is_active=0`，ES/Milvus同步标记；**与 `lifecycle_status` 联动**：当文档变为 `archived` 或 `rejected` 时，其下所有块 `is_active` 自动置0 |
| **版本更新期间的服务连续性** | 当 `lifecycle_status = 'pending_approval'` 时，**旧版本块继续保持 `is_active=1`**，用户检索不受影响；审批通过重新索引完成前，`indexing_status` 临时置 `0`，完成后切换至新块，旧块置 `0` |
| **关键ID** | `chunk_uuid` 是三库连接的唯一桥梁 |
| **父子块关系** | 子块通过 `parent_chunk_id` 关联父块；父块仅存MySQL |
| **溯源链路** | `kb_chunks.source_elem_ids` → `elements.json` → 提取 `bbox` 坐标 |
| **全链路闭环** | `trace_id` 贯穿 `kb_router_logs` → `kb_query_logs` → `kb_search_logs` → `kb_rank_logs` → `kb_user_feedback`（单轮检索）；**多步规划场景下**：`kb_query_logs` → `kb_agent_loop_traces` → `kb_evaluation_results` → `kb_pending_questions` |
| **MCP配置热加载** | `kb_mcp_providers` 和 `kb_mcp_weight_mapping` 定时刷新（每5分钟） |
| **MCP缓存失效** | 定时清理 `kb_mcp_cache` 中已过期的记录 |
| **通知补偿** | 定时扫描 `kb_notification_logs` 中 `status=0` 且超过1分钟的记录，触发重发（最多3次） |
| **Agent循环状态恢复（v6.3新增）** | 当用户回复反问时，通过 `trace_id` 查询 `kb_sessions.agent_state`，反序列化后注入 LangGraph 的 `Checkpoint`，从中断处继续执行 |
| **反问超时清理（v6.3新增）** | 定时任务扫描 `kb_pending_questions` 中 `status=0` 且 `expires_at < NOW()` 的记录，自动更新 `loop_status='rejected'` 并释放资源 |
| **Agent成本分摊（v6.3新增）** | 通过 `kb_agent_loop_traces` 中的 `llm_prompt_tokens` + `llm_completion_tokens` 汇总每一次多步规划的总 Token 消耗，便于向业务部门分摊成本 |
