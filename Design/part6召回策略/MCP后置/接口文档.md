# 任务6 召回策略 — 接口设计文档（供 Dify 集成）

> **版本**：v1.0  
> **状态**：已定稿  
> **适用对象**：Dify 编排层开发者、后端开发人员  

## 一、概述

### 1.1 定位

任务6（召回策略）是知识库查询链路中的核心环节。本服务接收上游（任务5）处理后的查询信息，执行多路召回（语义检索、关键词检索、模糊匹配），并通过 RRF 融合排序后返回候选 Chunk 列表。

本服务以 **RESTful API** 形式对外暴露，Dify 通过 **HTTP 请求节点**（或自定义节点）调用。

### 1.2 上下游关系

```
┌─────────┐    ┌──────────────┐    ┌─────────────┐    ┌─────────────┐
│  Dify   │───▶│  任务5:意图   │───▶│ 任务6:召回   │───▶│ 任务7:排序   │
│ 编排层  │    │  理解/改写    │    │  (本服务)    │    │             │
└─────────┘    └──────────────┘    └─────────────┘    └─────────────┘
```

### 1.3 Dify 集成方式

在 Dify 工作流或 Chatflow 中，使用 **HTTP 请求节点** 调用本服务的 `/api/v1/search` 接口，传入查询文本、向量、过滤条件等，获取召回结果后继续流转。

## 二、API 接口规范

### 2.1 基础信息

| 项目 | 说明 |
| :--- | :--- |
| **Base URL** | `http://{your-search-service}/api/v1` |
| **认证方式** | API Key（Bearer Token），通过环境变量 `SEARCH_API_KEY` 配置 |
| **超时** | 建议 5s（可调），本服务内部超时 3s |
| **响应格式** | JSON |

### 2.2 核心接口：`POST /search`

#### 请求头

```
Authorization: Bearer {search_api_key}
Content-Type: application/json
```

#### 请求体（Request Body）

| 字段 | 类型 | 必填 | 描述 |
| :--- | :--- | :--- | :--- |
| `request_id` | string | 是 | 全链路追踪 ID，由 Dify 生成，用于日志关联 |
| `session_id` | string | 否 | 会话 ID（用于多轮对话上下文） |
| `query` | string | 是 | 用户原始查询（或改写后的主查询） |
| `query_embedding` | array[float] | 是 | 查询向量（1536 维），由 Dify 调用 Embedding 模型生成 |
| `rewritten_query` | string | 否 | 改写后的查询（如存在） |
| `sub_questions` | array[string] | 否 | 拆解后的子问题列表（用于多路并行检索） |
| `intent` | object | 否 | 意图分类结果（类型、置信度等） |
| `source_kb` | string | 否 | 路由指定的知识库名称（如 `stock`），用于过滤 |
| `tag_filters` | array[string] | 否 | 标签筛选列表（如 `["财务分析"]`） |
| `tag_match_mode` | string | 否 | 标签匹配模式：`exact`（默认）、`any`、`all` |
| `entity_codes` | array[string] | 否 | 投研实体代码列表（如 `["600519"]`） |
| `entity_expand` | boolean | 否 | 是否展开关联实体（默认 `false`） |
| `top_k` | integer | 否 | 最终返回结果数（默认 20，最大 100） |
| `semantic_top_k` | integer | 否 | 语义通路召回数量（默认 50） |
| `keyword_top_k` | integer | 否 | 关键词通路召回数量（默认 50） |
| `debug` | boolean | 否 | 是否返回调试信息（默认 `false`） |

**示例**：

```json
{
  "request_id": "req_20260805_001",
  "session_id": "sess_abc123",
  "query": "茅台2024年业绩增长原因",
  "query_embedding": [0.123, -0.456, ...],
  "rewritten_query": "贵州茅台 2024年度 业绩增长 驱动因素",
  "sub_questions": [
    "茅台2024年营收增长多少",
    "茅台2024年利润增长原因"
  ],
  "source_kb": "stock",
  "tag_filters": ["财务分析"],
  "tag_match_mode": "any",
  "entity_codes": ["600519"],
  "entity_expand": false,
  "top_k": 20,
  "semantic_top_k": 50,
  "keyword_top_k": 50,
  "debug": false
}
```

#### 响应体（Response Body）

**成功（HTTP 200）**：

| 字段 | 类型 | 描述 |
| :--- | :--- | :--- |
| `code` | integer | 0 表示成功 |
| `message` | string | 提示信息 |
| `data` | object | 结果数据 |
| `data.request_id` | string | 回传请求 ID |
| `data.results` | array[object] | 召回结果列表 |
| `data.results[].chunk_uuid` | string | Chunk 唯一标识 |
| `data.results[].doc_id` | integer | 文档 ID |
| `data.results[].content_text` | string | Chunk 文本内容 |
| `data.results[].parent_chunk_id` | string | 父块 ID（可为空） |
| `data.results[].source_kb` | string | 来源知识库 |
| `data.results[].tags` | array[string] | 标签列表 |
| `data.results[].rrf_score` | float | RRF 融合分数 |
| `data.results[].scores` | object | 各通路得分（语义、关键词等） |
| `data.results[].found_in` | array[string] | 命中的通路名称列表 |
| `data.results[].metadata` | object | 文档元数据（标题、日期、章节等） |
| `data.total_candidates` | integer | 融合前候选总数 |
| `data.fusion_stats` | object | RRF 统计信息（各通路命中数、重叠数等） |
| `data.latency_ms` | integer | 服务处理耗时（毫秒） |
| `data.fallback_triggered` | boolean | 是否触发宽松召回 |

**示例**：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "request_id": "req_20260805_001",
    "results": [
      {
        "chunk_uuid": "chunk_001",
        "doc_id": 12345,
        "content_text": "贵州茅台2024年实现营业收入...",
        "parent_chunk_id": "parent_001",
        "source_kb": "stock",
        "tags": ["财务分析", "年报解读"],
        "rrf_score": 0.0143,
        "scores": {
          "semantic": 0.89,
          "keyword": 0.76
        },
        "found_in": ["semantic", "keyword"],
        "metadata": {
          "doc_title": "贵州茅台2024年年度报告",
          "published_date": "2025-04-15",
          "chapter": "经营情况讨论与分析"
        }
      }
    ],
    "total_candidates": 120,
    "fusion_stats": {
      "semantic_hits": 45,
      "keyword_hits": 38,
      "overlap": 25,
      "rrf_k": 60
    },
    "latency_ms": 187,
    "fallback_triggered": false
  }
}
```

**失败（HTTP 非 200）**：

| 字段 | 类型 | 描述 |
| :--- | :--- | :--- |
| `code` | integer | 错误码（见下表） |
| `message` | string | 错误描述 |
| `request_id` | string | 回传请求 ID（便于追踪） |

**错误码表**：

| 错误码 | 说明 | 处理建议 |
| :--- | :--- | :--- |
| 4001 | 请求参数错误（缺少必填字段、embedding 维度不匹配等） | 检查请求体 |
| 4002 | 标签不存在（`tag_filters` 中的标签在系统中不存在） | 校验标签名称 |
| 4003 | 实体代码不存在 | 校验实体代码 |
| 5001 | 语义检索服务异常（Milvus 不可用） | 重试或降级 |
| 5002 | 关键词检索服务异常（ES 不可用） | 重试或降级 |
| 5003 | 融合排序异常 | 检查日志 |
| 5004 | 超时（>3s） | 缩小 `top_k` 或重试 |

### 2.3 辅助接口：`GET /health`

用于 Dify 健康检查，返回服务状态。

**请求**：
```
GET /health
Authorization: Bearer {search_api_key}
```

**响应**：
```json
{
  "status": "ok",
  "version": "1.0.0"
}
```

## 三、Dify 集成示例

### 3.1 在 Dify 工作流中使用 HTTP 请求节点

1. **添加 HTTP 请求节点**，配置如下：

   - **方法**：`POST`
   - **URL**：`{{env.SEARCH_SERVICE_URL}}/api/v1/search`（可配置为环境变量）
   - **Headers**：
     - `Authorization: Bearer {{env.SEARCH_API_KEY}}`
     - `Content-Type: application/json`
   - **Body**：选择 `raw JSON`，使用变量填充

2. **Body JSON 模板**（引用上游节点变量）：

   ```json
   {
     "request_id": "{{sys.workflow_run_id}}",
     "session_id": "{{session_id}}",
     "query": "{{intent_understanding.rewritten_query}}",
     "query_embedding": {{embedding_node.embedding}},
     "source_kb": "{{router_node.source_kb}}",
     "tag_filters": {{router_node.filter_tags}},
     "entity_codes": {{router_node.entity_codes}},
     "top_k": 20
   }
   ```

   > 注意：`query_embedding` 需要由上游 **Embedding 节点** 生成，该节点调用 Embedding 模型将 `query` 转为向量。

3. **处理响应**：HTTP 请求节点的输出变量为 `body`，可通过 `{{http_node.body.data.results}}` 引用召回结果，传递给后续节点（如排序节点）。

### 3.2 完整工作流片段示意

```
[用户输入] → [任务5:意图理解] → [Embedding模型] → [HTTP请求(任务6)] → [任务7:排序] → [输出]
                                    │
                                    └─ 生成 query_embedding
```

### 3.3 环境变量配置（Dify 中）

在 Dify 的 **环境变量** 中设置：

- `SEARCH_SERVICE_URL`：例如 `http://search-service:8080`
- `SEARCH_API_KEY`：服务鉴权密钥

## 四、降级与容错

- 若语义检索（Milvus）不可用，服务自动降级为仅关键词检索（ES），并标记 `fallback_triggered=true`。
- 若全部通路失败，返回空结果并记录错误日志。
- Dify 可配置 HTTP 请求节点的 **重试策略**（如重试 2 次，间隔 1s）。

## 五、性能与监控

- **日志表**：`kb_search_logs`（已在数据模型 v4.0 中定义），用于记录每次召回详情。
- **监控指标**：
  - 请求量、成功率、平均延迟
  - 各通路命中率、重叠率
  - 宽松召回触发频率
