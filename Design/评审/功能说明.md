## 一、项目背景与建设目标

### 1.1 为什么要建这个系统？

我司作为资产管理机构，日常运作高度依赖**专业知识**的支撑——基金经理需要实时查阅基金净值与持仓数据，信评分析师需要追踪债券信用评级变化，合规人员需要随时检索监管政策与内部制度，风控人员需要评估各类风险指标……然而，这些知识分散在**9个不同的业务系统**中，形成了典型的**知识孤岛**：

- 基金数据在基金系统，合规文件在OA系统，信评报告在另一个平台
- 同一个问题可能需要跨多个系统查询，效率低下
- 新员工入职后需要花费大量时间熟悉各系统的入口和查询方式
- 知识更新后，旧版本仍在各系统中散落，难以追溯

**统一知识库门户**的目标，就是**将这9个知识库整合到一个统一的AI问答入口中**，让员工像使用搜索引擎一样，用自然语言提问，就能获得精准的答案，并附上可靠的来源依据。

### 1.2 覆盖范围

本项目覆盖**9个业务知识库**：

| 序号 | 知识库名称 | 主要服务对象 | 典型内容 |
| :--- | :--- | :--- | :--- |
| 1 | 基金知识库 | 基金经理、产品经理 | 基金净值、持仓、业绩、产品要素 |
| 2 | 合规知识库 | 合规审核、法务 | 监管政策、适当性管理、反洗钱、廉洁从业 |

| 4 | 量化知识库 | 量化研究员 | 量化模型、因子数据、回测结果 |
| 5 | 运营知识库 | 运营人员 | 运营流程、清算规则、制度规范 |
| 6 | 固收投研知识库 | 固收研究员 | 利率债、信用债、宏观策略 |

## 三、核心功能详解

### 3.1 文档管理：知识的“入库”

**这个功能解决什么问题？**
> 9个知识库的文档分散在各处，格式不一（PDF、Word、Excel等），人工整理和索引困难。系统需要自动完成文档的解析、切分和索引，让知识“可用”。

#### 3.1.1 文档上传与自动处理

用户上传一份文档（如PDF研报）后，系统自动完成以下流程：

| 步骤 | 做什么 | 用户看到什么 |
| :--- | :--- | :--- |
| **① 版本检测** | 计算文件Hash，判断是新文档、更新还是重复 | 实时反馈处理状态 |
| **② 智能解析** | 调用MinerU引擎解析文档结构（标题、段落、表格、图片） | 处理进度（解析中…） |
| **③ 父子切块** | 按章节组装“父块”（完整上下文），再切分为“子块”（用于检索） | 处理进度（切块中…） |
| **④ 三库索引** | 子块写入ES（关键词检索）和Milvus（向量检索），元数据写入MySQL | 处理完成，可检索 |

> **父子块结构说明**：子块约256个Token，用于精确匹配用户问题；父块是完整的章节内容，当子块被命中时，返回其所属的父块作为上下文。这样既保证了检索精度，又确保了大模型能获得完整的背景信息。

**用户操作**：在门户页面上传文件 → 选择所属知识库 → 填写元数据（发布日期、标签等）→ 提交。

#### 3.1.2 文档版本管理与审批

资管行业对文档的**准确性和合规性**有极高要求。系统设计了完整的版本管理机制：

**场景示例**：合规部更新了《反洗钱管理制度》V3.0。

| 阶段 | 系统行为 | 相关人员 |
| :--- | :--- | :--- |
| **① 检测变更** | 上传新文件后，系统检测到Hash变化，自动识别为“版本升级” | 上传者 |
| **② 进入待审** | 旧版本(V2.0)继续服务，新版本(V3.0)进入 `pending_approval` 状态 | 系统自动 |
| **③ 发送通知** | 系统自动发送邮件/待办提醒给合规负责人 | 合规负责人 |
| **④ 人工审批** | 负责人在后台查看变更摘要，点击“批准”或“驳回” | 合规负责人 |
| **⑤ 执行更新** | 批准后，系统执行差量索引（仅更新变化的块），新版本生效 | 系统自动 |
| **⑥ 记录留痕** | 所有操作（谁、何时、批准/驳回）全量记录，满足审计要求 | 系统自动 |

> **关键设计**：审批期间旧版本继续服务，确保业务不中断。

### 3.2 智能问答：知识的“消费”

**这个功能解决什么问题？**
> 员工面对9个知识库，不知道该去哪个库查；同一个问题在不同库可能有不同答案；简单问题直接回答，复杂问题需要多步推理。系统需要像“智能导航+超级搜索”一样工作。

#### 3.2.1 智能路由：该去哪个知识库找答案？

当用户输入一个问题时，系统首先判断**这个问题应该去哪个知识库**。

**路由决策 = 静态规则 + 动态信号**

| 决策来源 | 说明 | 示例 |
| :--- | :--- | :--- |
| **静态关键词规则** | 根据预置的关键词-知识库映射表 | “净值”→基金库；“评级”→信评库 |
| **MCP动态信号** | 实时接入外部业务系统的信号，动态调整路由权重 | 某债券被列入风险观察名单 → 路由优先指向风控库 |
| **上下文偏置** | 用户当前所在的知识库，给予适当加分 | 用户在固收投研页面提问 → 固收库权重+5% |
| **歧义处理** | 当多个知识库得分接近时，反问用户确认 | “您的问题涉及固收投研和信评两个库，请选择…” |

**MCP动态信号的价值**：传统路由是“死配置”，关键词映射需要人工维护。MCP让路由具备了**实时感知能力**——当外部系统（如风控系统）发出某债券的风险预警时，系统会**自动将相关查询导向风控知识库**，即使问题本身没有提到“风控”二字。

#### 3.2.2 意图理解：用户到底想问什么？

路由确定了“去哪里找”，接下来要理解“用户到底想问什么”。

| 意图类型 | 说明 | 示例 |
| :--- | :--- | :--- |
| **FACTUAL（事实查询）** | 查询某个确定的事实或数值 | “XX债券的最新评级是多少？” |
| **ANALYTICAL（分析推理）** | 需要综合多信息进行判断 | “城投债的信用利差怎么看？” |
| **CALCULATION（数据计算）** | 需要进行计算或统计 | “近一年基金收益率平均值是多少？” |
| **CHITCHAT（闲聊）** | 非业务类问候 | “你好” |

**对于ANALYTICAL类型**，系统还会：
- **拆解子问题**：将复杂问题拆解为多个子问题（如“城投债信用利差怎么看？”拆解为“城投债整体走势”+“信用利差分析”+“配置建议”）
- **改写查询**：将口语化问题改写为适合检索的规范化表述（如“那个AAA城投怎么样”改写为“AAA评级城投公司信用风险分析报告”）
- **扩展同义词**：自动补充同义词和相关术语

#### 3.2.3 混合检索：如何找到最相关的内容？

系统采用**三路并行召回 + 可选精排**的策略：

```
用户问题 → 生成向量 → 并行执行三条检索通路
            │
            ├── 语义检索（Milvus）：理解问题含义，找到语义相似的内容
            ├── 关键词检索（ES）：精确匹配专业术语和实体名称
            └── 模糊检索（ES）：处理拼写错误和近似表达
            │
            ▼
        结果融合（RRF）→ 可选Rerank精排 → 输出Top-K候选
```

**RRF（倒数排名融合）**：将三条通路的检索结果按排名融合，综合打分。

**Rerank（可选精排）**：使用Cross-Encoder模型对候选结果进行深度语义精排。这是一个**可插拔的高级特性**——默认关闭，可通过配置一键开启，用于A/B测试验证效果。

#### 3.2.4 排序加权：谁排在前面？

召回阶段找到了一批候选内容，但还需要根据**业务规则**进行排序——不是所有相关内容都同等重要。

| 排序因子 | 说明 | 示例 |
| :--- | :--- | :--- |
| **相关性** | 与用户问题的语义匹配程度 | 来自召回阶段的 `recall_score` |
| **权威性** | 文档来源的可信度 | 监管公告 > 内部研报 > 外部资讯 |
| **时效性** | 文档发布时间的衰减 | 近7天发布的文档权重最高，越旧衰减越大 |
| **用户角色** | 不同角色关注点不同 | 合规审核更看重权威性，交易员更看重时效性 |
| **多样性** | 避免同一文档霸屏 | 同一文档最多返回3个块 |

#### 3.2.5 多步规划：复杂问题如何处理？

有些问题不是一次检索能解决的，需要**多轮推理**。系统内置了**ReAct模式**的Agent：

```
用户提问 → 第1轮：思考→检索→评估（置信度不足）→ 继续
         → 第2轮：思考→细化检索→评估（置信度仍不足）→ 反问用户
         → 用户补充信息 → 第3轮：检索→评估（置信度达标）→ 生成答案
```

**自主评估**：每轮检索后，系统从**相关性、覆盖度、权威性、一致性**四个维度评估信息是否充分。根据评估结果自动决策：

| 评估结论 | 系统行为 |
| :--- | :--- |
| 信息充足 → **ANSWER** | 直接生成答案 |
| 信息不足但有方向 → **CONTINUE** | 进入下一轮检索 |
| 缺少关键信息 → **ASK** | 反问用户补充 |
| 严重不足或超出能力 → **REJECT** | 礼貌拒绝并说明原因 |

### 3.3 质量闭环：让系统越用越准

**这个功能解决什么问题？**
> AI问答不可能100%准确。当用户遇到“答非所问”时，系统需要能**发现问题、分析原因、推动改进**，并验证改进是否有效。

#### 3.3.1 反馈采集

用户可以对每次问答结果进行**点赞/点踩**，并可填写备注说明原因。系统自动记录：

- 用户的原始问题
- 系统改写后的查询
- 路由决策结果
- 召回了哪些内容
- 排序结果

#### 3.3.2 根因分析（漏斗式）

点踩产生后，系统自动触发根因分析，采用**三层漏斗**策略：

| 层级 | 方法 | 适用场景 | 成本 |
| :--- | :--- | :--- | :--- |
| **第一层：规则初筛** | 预置规则快速判断 | 明显的问题（如召回数为0） | 极低 |
| **第二层：LLM深度分析** | 调用大模型进行归因 | 规则无法判断的复杂情况 | 中等 |
| **第三层：人工复核** | 转交业务专家判断 | 置信度低于0.6的情况 | 较高 |

**分析结果**：系统输出问题分类（路由错误/意图错误/召回失败/排序偏差/知识缺失/生成错误）、根因描述、优化建议及置信度。

#### 3.3.3 优化建议与审批

分析完成后，系统生成优化建议，进入**人工审批流程**：

```
建议生成 → 待审批 → 人工批准/驳回 → 实施变更 → 自动回归验证 → 闭环完成
```

**优化建议类型**：

| 类型 | 说明 | 对接模块 |
| :--- | :--- | :--- |
| **配置调优** | 调整路由关键词、排序权重等 | 任务4/7（Apollo配置） |
| **文档重索引** | 知识缺失场景，更新文档版本 | 任务8（版本管理） |
| **路由规则更新** | 新增或修改关键词映射 | 任务4（路由配置） |

**自动回归验证**：优化实施后，系统自动触发任务10的评测流水线，用**黄金问答集**验证指标是否提升。若指标下降，自动回滚并告警。


## 四、技术特色与亮点

### 4.1 架构上的三个“可插拔”

| 可插拔能力 | 说明 | 业务价值 |
| :--- | :--- | :--- |
| **解析引擎可替换** | 当前用MinerU，未来可换为自研OCR或其他解析服务 | 不锁定单一供应商 |
| **Rerank可开关** | 通过配置一键开启/关闭Cross-Encoder精排 | 低成本A/B测试 |
| **MCP动态信号可扩展** | 路由信号来源可随时接入新的业务系统 | 路由能力持续增强 |

### 4.2 全文检索与向量检索双轨并行

系统同时部署了**Elasticsearch（关键词检索）** 和**Milvus（向量检索）**：

| 检索方式 | 擅长场景 | 技术实现 |
| :--- | :--- | :--- |
| **关键词检索（ES）** | 精确匹配专业术语、代码、名称 | BM25算法 |
| **向量检索（Milvus）** | 理解问题含义、语义相似 | ANN近似最近邻 |
| **混合检索** | 综合两者优势 | RRF融合 + 可选Rerank |

### 4.3 父子块结构兼顾精度与完整性

| 块类型 | 用途 | 存储位置 |
| :--- | :--- | :--- |
| **子块（~256 tokens）** | 用于检索匹配 | ES + Milvus |
| **父块（完整章节）** | 作为上下文返回给大模型 | 仅MySQL |

检索时**只搜索子块**，返回时**附带父块**，既保证了匹配精度，又确保了大模型有足够的上下文生成答案。

### 4.4 端到端的质量保障体系

```
文档上传 → 版本审批 → 智能问答 → 用户反馈 → 根因分析 → 优化实施 → 回归验证
   ↑                                                                      │
   └──────────────────────── 闭环持续迭代 ──────────────────────────────────┘
```

系统构建了从**知识生产**到**知识消费**再到**质量改进**的完整闭环，确保知识库的质量随时间推移持续提升。

| **MySQL** | 元数据存储 | 文档元数据、切块原文、日志、配置表 |
| **Elasticsearch** | 检索引擎 | 关键词全文检索（BM25） |
| **Milvus** | 向量检索引擎 | 语义向量检索（ANN） |
| **MinIO** | 对象存储 | 原始文档文件、解析缓存 |
| **Apollo** | 配置中心 | 路由规则、排序权重等热配置管理 |


## 六、业务场景示例

### 场景一：基金经理查询基金数据

> **用户**：“帮我查一下XX基金近一年的收益率和最大回撤”
>
> **系统行为**：
> 1. 路由判断 → 问题含“基金”“收益率”→ 路由至**基金知识库**
> 2. 意图识别 → FACTUAL（事实查询）
> 3. 改写查询 → “XX基金 近一年 收益率 最大回撤”
> 4. 检索召回 → 从基金知识库中召回相关文档片段
> 5. 排序 → 按相关性+时效性排序
> 6. 生成答案 → 返回具体数据并附上来源

### 场景二：合规人员查询监管政策

> **用户**：“最近反洗钱有什么新规定？”
>
> **系统行为**：
> 1. 路由判断 → 静态规则命中“反洗钱”→ 路由至**合规知识库**
> 2. MCP增强 → 外部监管动态服务返回“近期有新政发布”→ 合规库权重+1.5
> 3. 意图识别 → ANALYTICAL（分析推理）
> 4. 拆解子问题 → “反洗钱最新监管政策”+“对业务的影响”
> 5. 检索→评估→回答

### 场景三：信评分析师评估债券风险

> **用户**：“XX城投债的信用风险怎么样？”
>
> **系统行为**：
> 1. 路由判断 → 命中“城投债”“信用”→ 路由至**信评知识库**和**固收投研库**
> 2. MCP增强 → 风控系统返回“该主体被列入观察名单”→ 风控库权重+0.9
> 3. 最终路由 → **信评库 + 风控库**（MCP动态干预）
> 4. 多步规划 → 先查评级→再查舆情→综合评估
> 5. 生成答案 → 附带“该主体已被列入风险观察名单”的风险提示


## 七、总结

统一知识库门户通过**文档自动入库、智能路由问答、质量反馈闭环**三大核心能力，将分散在9个业务系统中的知识整合为一个统一的AI问答入口。

**对员工**：告别“不知道去哪个系统查”，像用搜索引擎一样提问即可获得答案。

**对管理者**：知识资产统一沉淀、版本可控、质量可度量、持续可优化。

**对合规**：所有知识变更全链路审计，AI回答附来源引用，可追溯、可验证。
